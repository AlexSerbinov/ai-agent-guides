# Review Loop

Ітеративна система код рев'ю, яка запускає 6 паралельних агентів, агрегує знахідки, застосовує безпечні фікси та повторює цикл поки скор не досягне 95% або вище.

**НІКОЛИ не комітить.** Тільки рев'ює та фіксить код. Юзер сам вирішує коли комітити.

## Передумови

- `codex` CLI встановлений та авторизований (`codex login`)
- `gemini` CLI встановлений та авторизований
- Ми в git-репозиторії з незакоміченими змінами (staged + unstaged)
- `jq` доступний для парсингу JSON

### Правила логування

1. **Логувати ПОВНИЙ вивід кожного агента** — не підсумовувати і не скорочувати. Лог — це джерело правди.
2. **Логувати КОЖНУ зміну коду** з before/after фрагментами — щоб можна було відстежити що саме змінив цикл.
3. **Логувати навіть невдалих агентів** — записувати що пішло не так (таймаут, помилка CLI тощо).
4. **Логувати часові мітки** — для кожного початку ітерації.
5. **Дописувати, ніколи не перезаписувати** — кожна ітерація додається до того самого файлу.
6. **Використовувати Write** для створення файлу на Кроці 1, потім **Edit** для додавання нових ітерацій.
7. **Лог-файл залишається після завершення циклу** — це постійний запис у репозиторії.

## Агенти рев'ю

Всі 6 агентів запускаються **паралельно** на кожній ітерації.

### Claude Агент 1 — Загальне рев'ю #1

**Тип:** `Agent` tool, `subagent_type: "general-purpose"`

**Промпт:**
```
Ти — досвідчений код-рев'юер. Проаналізуй ВСІ незакомічені зміни (як staged, так і unstaged) в цьому репозиторії.

Виконай ці команди щоб отримати зміни:
1. `git diff` (unstaged зміни)
2. `git diff --cached` (staged зміни)
3. `git diff HEAD` (всі незакомічені vs HEAD)
4. `git status --short`

Надай структуроване код рев'ю з рівнями серйозності:
- **Критична** — спричинить баги, падіння або втрату даних на проді
- **Висока** — значні логічні помилки, race conditions, відсутня обробка помилок
- **Середня** — проблеми якості коду, продуктивності, незрозуміла логіка
- **Низька** — стилістичні проблеми, незначні покращення, пропозиції щодо нейменгу

Для кожної знахідки:
1. Шлях до файлу та номер(и) рядків
2. В чому проблема
3. Чому це важливо
4. Запропонований фікс (конкретний код)

Фокус: баги, логічні помилки, edge cases, обробка помилок, продуктивність.
Будь конкретним та практичним. НЕ пропонуй зміни що змінюють бізнес-логіку, якщо вона не явно поламана.
Весь вивід має бути англійською мовою (код, коментарі, назви змінних).

НЕ ВНОСИ жодних змін. Тільки повідомляй знахідки.
```

### Claude Агент 2 — Загальне рев'ю #2 (Друга думка)

**Тип:** `Agent` tool, `subagent_type: "general-purpose"`

**Промпт:**
```
Ти — незалежний код-рев'юер, який надає другу думку. Проаналізуй ВСІ незакомічені зміни в цьому репозиторії.

Виконай ці команди щоб отримати зміни:
1. `git diff HEAD` (всі незакомічені зміни)
2. `git status --short`
3. Прочитай кожен змінений файл повністю щоб зрозуміти контекст навколо

Надай свіже, незалежне рев'ю — НЕ передбачай що можуть знайти інші рев'юери. Дивись на речі під іншим кутом.

Фокус:
- Речі які легко пропустити: off-by-one помилки, null/undefined кейси, async/await проблеми
- Порушення API контрактів: чи відповідає код очікуваним інтерфейсам?
- Потік даних: чи трансформації коректні end-to-end?
- Пропагація помилок: чи помилки перехоплюються, логуються та обробляються правильно?
- Нейменг та читабельність: чи хтось інший зрозуміє це через 6 місяців?

Оцінюй кожну знахідку: Critical / High / Medium / Low.
Вказуй шлях до файлу, номери рядків та конкретні пропозиції фіксів.
Весь вивід має бути англійською мовою.

НЕ ВНОСИ жодних змін. Тільки повідомляй знахідки.
```

### Claude Агент 3 — Детектор ламаючих змін

**Тип:** `Agent` tool, `subagent_type: "general-purpose"`

**Промпт:**
```
Ти — аналітик регресій. Твоє ЄДИНЕ завдання — визначити чи незакомічені зміни можуть поламати будь-яку ІСНУЮЧУ функціональність.

Виконай ці команди:
1. `git diff HEAD` (всі незакомічені зміни)
2. `git status --short`
3. Для кожного зміненого файлу прочитай ПОВНИЙ файл (не тільки diff) щоб зрозуміти контекст
4. Знайди всіх викликачів/споживачів змінених функцій, класів або API

Перевір:
- **Зміни API контракту**: перейменовані поля, змінені типи, видалені ендпоінти, змінені форми відповідей
- **Зміни схеми бази даних**: чи існуючі дані поламаються? Чи потрібні міграції?
- **Зміни імпортів/експортів**: видалені експорти від яких залежать інші модулі
- **Поведінкові зміни**: функції що тепер повертають інші значення, кидають інші помилки, або мають інші побічні ефекти
- **Зміни конфігурації**: перейменовані/видалені env змінні, змінені значення за замовчуванням
- **Зміни типів**: модифікації TypeScript інтерфейсів що ламають споживачів

Для кожної потенційно ламаючої зміни:
1. Що змінилось (file:line)
2. Що може поламатись (список конкретних файлів/модулів/споживачів)
3. Рівень ризику: Critical / High / Medium / Low
4. Як перевірити: конкретна тестова команда або ручна перевірка

Якщо ламаючих змін НЕ знайдено, явно вкажи: "No breaking changes detected."
Весь вивід має бути англійською мовою.

НЕ ВНОСИ жодних змін. Тільки повідомляй знахідки.
```

### Claude Агент 4 — Рев'ю безпеки

**Тип:** `Agent` tool, `subagent_type: "general-purpose"`

**Промпт:**
```
Ти — аудитор безпеки. Перевір ВСІ незакомічені зміни на вразливості безпеки.

Виконай ці команди:
1. `git diff HEAD` (всі незакомічені зміни)
2. `git status --short`
3. Прочитай повні файли де виявлено зміни пов'язані з безпекою

Фокусуйся ВИКЛЮЧНО на:
- **Ін'єкції**: SQL injection, command injection, XSS, template injection
- **Автентифікація/Авторизація**: обробка JWT, управління сесіями, перевірки ролей, відсутні гарди
- **Витік даних**: чутливі дані в логах, відповідях або повідомленнях помилок; .env секрети, API ключі
- **Валідація вводу**: відсутня валідація, проблеми приведення типів, buffer overflow
- **OWASP Top 10**: всі категорії
- **Криптографічні проблеми**: слабкі алгоритми, захардкоджені ключі, небезпечний рандом
- **Ризики залежностей**: відомо вразливі пакети, небезпечні імпорти
- **Race conditions**: TOCTOU, подвійне списання, конкурентний доступ без блокувань

Для кожної вразливості:
1. Шлях до файлу та номер(и) рядків
2. Тип вразливості (CWE номер якщо можливо)
3. Серйозність: Critical / High / Medium / Low
4. Сценарій експлуатації (як це може бути атаковано)
5. Конкретний фікс

Якщо вразливостей безпеки НЕ знайдено, явно вкажи: "No security vulnerabilities detected."
Весь вивід має бути англійською мовою.

НЕ ВНОСИ жодних змін. Тільки повідомляй знахідки.
```

### Codex Агент — Загальне рев'ю

**Тип:** `Bash` tool з `run_in_background: true`

Запускає той самий підхід що й скіл `codex-review-all`.

**КРИТИЧНО: `--uncommitted` та `[PROMPT]` є ВЗАЄМОВИКЛЮЧНИМИ в Codex CLI.**

```bash
codex exec review --uncommitted --ephemeral --json 2>/dev/null | jq -rs '[.[] | select(.type == "item.completed" and .item.type == "agent_message") | .item.text] | join("\n")'
```

### Gemini Агент — Архітектура та якість коду

**Тип:** `Bash` tool з `run_in_background: true`

Використовує Gemini CLI з `@` посиланнями на файли для повного контексту.

**Крок 1:** Отримати посилання на змінені файли:
```bash
git diff --name-only HEAD
```

**Крок 2:** Запустити рев'ю:
```bash
gemini -p "Ти — архітектор програмного забезпечення та експерт з якості коду. Перевір незакомічені зміни: <@FILE_REFERENCES>

Ось git diff:

$(git diff HEAD | head -5000)

Фокусуй рев'ю ВИКЛЮЧНО на:
1. **Архітектура**: Чи зміни в правильному місці? Чи вони слідують існуючим патернам? Розділення відповідальностей?
2. **Чистота коду**: Мертвий код, невикористані імпорти, дубльована логіка, надмірно складні функції
3. **Коментарі**: Чи складні частини задокументовані? Чи коментарі точні та англійською мовою?
4. **Swagger/OpenAPI**: Чи нові ендпоінти задокументовані з @ApiOperation, @ApiResponse, @ApiProperty? Чи DTO правильно анотовані?
5. **Нейменг**: Чи назви змінних/функцій/класів зрозумілі, консистентні та англійською?
6. **Порушення DRY**: Чи є скопійований код який варто виділити?

Оцінюй кожну знахідку: Critical / High / Medium / Low.
Будь конкретним — вказуй точні шляхи до файлів та номери рядків.
Весь вивід має бути англійською мовою." -m gemini-2.5-pro --output-format text 2>&1
```

## Потік виконання

### Крок 1: Перевірити наявність змін та ініціалізувати лог

```bash
git status --short
```

Якщо виводу немає → повідомити юзеру "Незакомічених змін не знайдено" і зупинитись.

Також виконати щоб зрозуміти масштаб:
```bash
git diff --stat HEAD
```

**Створити лог-файл:**
```bash
mkdir -p docs/review-logs
```

Використати `Write` tool щоб створити `docs/review-logs/YYYY-MM-DD-HH-MM-review-loop.md` з секцією заголовку (Початок, Репозиторій, Гілка, Початкові зміни). Використовувати актуальну поточну дату/час.

### Крок 2: Показати заголовок ітерації

Для ітерації N показати:

```
═══════════════════════════════════════════════════
  REVIEW LOOP — Ітерація #N
═══════════════════════════════════════════════════
```

### Крок 3: Запустити всі 6 агентів паралельно

Запустити ВСІ агенти одночасно:
- 4 Claude агенти через `Agent` tool з `run_in_background: true`
- 1 Codex агент через `Bash` tool з `run_in_background: true`
- 1 Gemini агент через `Bash` tool з `run_in_background: true`

**КРИТИЧНО:** Всі 6 мають бути запущені в ОДНОМУ повідомленні з кількома tool calls. Ніколи послідовно.

### Крок 4: Дочекатись всіх результатів та залогувати сирий вивід

Використати `TaskOutput` щоб зібрати результати від всіх 6 агентів по мірі їх завершення.

**ОДРАЗУ після завершення кожного агента** додати його сирий вивід до лог-файлу через `Edit` tool. НЕ чекати всіх агентів — логувати кожного по мірі надходження. Це гарантує що дані не втратяться навіть якщо процес перерветься.

Якщо якийсь агент впав (таймаут, падіння, помилка CLI):
- Залогувати невдачу (назва агента + повідомлення помилки) в лог-файл
- Продовжити з результатами від решти агентів
- Зазначити невдачу у звіті

### Крок 5: Агрегувати та дедуплікувати

Коли всі результати зібрані:

1. **Розпарсити всі знахідки** у єдиний список зі структурою:
   ```
   - Джерело: <який агент знайшов>
   - Серйозність: Critical / High / Medium / Low
   - Категорія: Bug / Security / Architecture / Breaking / Quality
   - Файл: <path:line>
   - Проблема: <опис>
   - Фікс: <запропонований фікс>
   ```

2. **Дедуплікувати**: Якщо кілька агентів позначили ту саму проблему (той самий файл + та сама тема), об'єднати їх в одну знахідку. Зазначити які агенти погодились.

3. **Крос-валідація**: Якщо Агент 3 (Ламаючі зміни) позначив щось як ризиковане, але запропонований фікс від Агента 1/2 спричинить цю поламку, позначити фікс як НЕБЕЗПЕЧНИЙ.

### Крок 6: Оцінити зміни (скорінг)

| Архітектура/чистота | 10% | 0-10 на основі відгуків агентів |

**Скор = max(0, 100 - загальні_вирахування)**

### Крок 8: Застосувати безпечні фікси

**ЗАСТОСОВУВАТИ ВСІ фікси що відповідають будь-якому з цих критеріїв:**
1. Серйозність Critical, High або Medium — фіксити автоматично без узгодження з юзером
2. Low серйозності — фіксити якщо фікс простий і однозначний (не потребує дизайн-рішень)
3. Фікс конкретний та однозначний (не "розгляньте рефакторинг")
4. Принаймні 1 агент знайшов проблему (не потрібна згода кількох агентів)

**Дозволені типи фіксів (будь-яка серйозність):**
   - Баги (логічні помилки, race conditions, off-by-one, null/undefined кейси)
   - Безпеку (валідація вводу, перевірки авторизації, запобігання ін'єкцій)
   - Обробку помилок (null перевірки, try-catch, правильні повідомлення помилок)
   - Якість коду (невикористані імпорти, мертвий код, друкарські помилки)
   - Типобезпеку (відсутні типи, неправильні типи)
   - Swagger анотації (відсутні @Api декоратори)
   - Архітектурні проблеми (якщо фікс зрозумілий і конкретний)
   - Зміни бізнес-логіки ДОЗВОЛЕНІ якщо поточна логіка явно поламана (підтверджено агентами)

**НЕ фіксити:**
   - Стилістичні переваги без конкретного бага
   - Зауваження типу "розгляньте рефакторинг" без конкретного коду
   - Інфраструктурні зміни (GitHub Secrets, CI/CD) — тільки звітувати

**При застосуванні фіксів:**
- Використовувати `Edit` tool для кожного фіксу
- Робити мінімальні, цільові зміни
- НЕ рефакторити оточуючий код
- НЕ додавати фічі
- НЕ змінювати форматування недоторканого коду
- **Логувати КОЖЕН фікс у лог-файл** з before/after фрагментами коду (див. Шаблон лог-файлу → секція "Застосовані зміни")

**Якщо безпечних фіксів НЕМАЄ** (всі знахідки Low/Medium або потребують ручного рев'ю):
- Перейти до Кроку 9 та звітувати знахідки
- Встановити скор поточний та запропонувати що юзеру варто переглянути вручну

## Важливі правила

1. **НІКОЛИ не комітити.** Тільки рев'юїти та фіксити. Юзер вирішує коли комітити.
2. **НІКОЛИ не змінювати бізнес-логіку.** Тільки фіксити баги, проблеми безпеки та якість коду.
3. **Весь вивід рев'ю має бути англійською.** Коментарі, swagger, назви змінних — все.
4. **Staged + unstaged = одне ціле.** Завжди використовувати `git diff HEAD` щоб бачити всі незакомічені зміни як єдине ціле.
5. **Максимум 5 ітерацій** щоб запобігти нескінченним циклам.
6. **Якщо Codex CLI недоступний** — пропустити цього агента і продовжити з 5 агентами.
7. **Якщо Gemini CLI недоступний** — пропустити цього агента і продовжити з 5 агентами.
8. **Мінімум 4 агенти мають відповісти** для валідної ітерації. Якщо менше 4 відповіли, перезапустити невдалих агентів один раз перед продовженням.
9. **Бути консервативним з авто-фіксами.** Коли є сумніви — звітувати замість фіксити.
10. **Кожна ітерація бачить ПОТОЧНИЙ стан** — після попередніх фіксів. Агенти завжди рев'юють найновіший код.
11. **ОБОВ'ЯЗКОВО вести лог-файл** — кожна ітерація, кожен агент, кожна зміна має бути записана.
