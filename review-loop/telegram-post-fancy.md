# Драфт 1 - Experiment Report

Я місяць тестував ідею: що якщо код ревʼю робити не одним агентом, а шістьма одночасно? Три різних AI-провайдери, шість різних фокусів, і зациклити поки не буде чисто.

Результат: з першого проходу знаходиться ~70% проблем. З другого - ще 20%. До третього - ловиться практично все, включно з race conditions які я б ніколи не побачив на ручному ревʼю.

Зробив із цього скіл `/review-loop` для Claude Code. Під капотом: 4 Claude агенти (баги, безпека, breaking changes, друга думка) + Codex + Gemini CLI. Всі паралельно. Результати агрегуються, дедуплікуються. Все що Critical/High - фікситься автоматично. Потім цикл повторюється на вже виправленому коді.

Мінуси: працює хвилин 15-20. Бізнес-логіку не чіпає - тільки технічні проблеми. Іноді false positives на першому проході (але другий прохід їх зазвичай відсіює).

Плюси: знаходить те, що ви пропустите. Race conditions, null dereference, відсутні перевірки авторизації, мертвий код. Все автоматично.

# Драфт 2 - Myth Buster

Один AI-агент для код ревʼю - це як один тестер на весь проект. Технічно працює. Практично - пропускає половину.

Проблема не в якості моделі. Проблема в тому, що коли агент знаходить критичний баг - він витрачає на нього весь контекст і пропускає дрібніші проблеми. Це не баг, це фізика контекстного вікна.

Рішення банальне: запустити кілька агентів з різним фокусом. Я довів це до крайності - 6 агентів паралельно від трьох різних провайдерів (Claude, Codex, Gemini). Кожен дивиться на код під своїм кутом: баги, безпека, breaking changes, архітектура.

Після першого проходу - автофікс. Після автофіксу - ті самі 6 агентів заново. Тепер критичне вже виправлене, і вони бачать те, що пропустили вперше. Цикл крутиться поки якість >= 95% або до 5 ітерацій.

Скіл називається `/review-loop`. Працює ~20 хвилин, але знаходить такі речі, які ви б зловили тільки на проді.

**Нюанс:** бізнес-логіку не рев'юїть. Тут потрібен 7-й агент - ви. Перегляньте що він нафіксив перед комітом.

# Драфт 3 - Deep Dive Teardown

Знаєте що будь-який AI-агент можна запустити в headless режимі? Тобто Claude Code може під капотом викликати Codex. А Codex - Gemini. Агенти можуть оркеструвати один одного.

```
claude -p "зроби код ревью"
```
```
codex --approval-mode full-auto -q "Review this code"
```

Я використав цю механіку для коду рев'ю. Зробив скіл `/review-loop` який запускає 6 агентів паралельно:

- 2x Claude - загальне ревʼю з різних кутів
- 1x Claude - детектор breaking changes (шукає всіх споживачів зміненого коду)
- 1x Claude - аудит безпеки (OWASP, інʼєкції, авторизація)
- 1x Codex - незалежний погляд від OpenAI
- 1x Gemini - архітектура, DRY, Swagger анотації

Кожен агент повертає знахідки зі severity (Critical/High/Medium/Low). Головний агент агрегує, прибирає дублі (якщо 3 з 6 знайшли те саме - це точно баг), рахує скор і автоматично фіксить все що Critical і High.

Далі - ключовий момент. Після фіксу весь цикл запускається заново. Шість свіжих агентів дивляться на вже виправлений код. Знаходять те, що пропустили вперше (бо тепер нема критичних проблем що забивали контекст). І так до 5 разів або поки скор >= 95%.

# Драфт 4 - TIL / Мікро-інсайт

TIL: якщо запустити 6 AI-рев'юерів паралельно і зациклити їх - вони знаходять баги які жоден з них не знайшов би поодинці.

# Драфт 5 - Decision Log ("Чому 6 агентів, а не 1")

Мені потрібно було автоматизоване код рев'ю перед комітами. Розглядав варіанти:

**1 агент (Claude або Codex)** - швидко, але пропускає ~40% проблем. Особливо security і breaking changes.

**2 агенти (Claude + Codex)** - краще, два різних погляди. Але все ще один прохід - критичні знахідки забивають контекст, дрібні пропускаються.

**6 агентів + цикл** - обрав цей варіант. Так, повільніше (до 20 хвилин). Але:
- Кожен агент має вузький фокус (баги / безпека / breaking / архітектура)
- Три різних провайдери (Claude, Codex, Gemini) - різні "сліпі зони"
- Цикл після автофіксу ловить те, що перший прохід пропустив
- Крос-валідація: якщо 3+ агенти знайшли те саме - це 100% проблема

**Що б зробив інакше:** додав би ще один агент на перевірку тестового покриття. І зменшив би таймаут для Gemini - іноді він думає занадто довго.

Скіл називається `/review-loop`. Працює в Claude Code.
