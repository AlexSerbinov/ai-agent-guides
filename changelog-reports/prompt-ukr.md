## End of Task Routine (Логування) — BLOCKING REQUIREMENT

**CRITICAL:** Ти НЕ МОЖЕШ завершити задачу поки не оновиш **ОБИДВА** лог-файли нижче. Це не опціонально — це обов'язковий крок завершення кожної задачі. Якщо завершив задачу без оновлення changelog і daily report — це помилка.

**Чекліст перед завершенням задачі (кожен раз, без винятків):**
- [ ] Записав у `changelog.md`
- [ ] Записав у `docs/reports/YYYY-MM-DD-daily-report.md`
- [ ] Тільки після цього завершую відповідь

Це робиш ти (основний агент), а не subagent — бо ти маєш повний контекст розмови і розумієш бізнес-задачу.

**Що писати:** фокусуйся на **бізнес-контексті** — яку проблему вирішували, яку задачу юзер описав, який результат. Не "змінив файл X", а "пофіксив баг з маппінгом мережі — USDT падав бо відправляли тікер без мережі".

### 1. Changelog — ОБОВ'ЯЗКОВО

Файл: `changelog.md` в корені проекту (або де він вже існує в проекті).

**Формат запису — детальний опис проблеми та рішення:**

```
## YYYY-MM-DD HH:MM — ProjectName

**Проблема:** Детально описати, яка проблема була — що не працювало, як це проявлялось, чому це було важливо. 1-2 речення.

**Рішення:** Що саме зробили для вирішення — який підхід обрали, що змінили, який результат. 1-3 речення.

**Деталі:** Додаткові нюанси — які файли/модулі зачеплено, чи впливає на фронтенд або інші сервіси, edge cases. Опціонально.
```

**Правила changelog:**
- Кожен запис — окремий `##` блок з датою, часом і назвою проекту
- Писати **бізнес-мовою** — не "змінив файл X", а "USDT свопи падали бо відправляли тікер без мережі"
- **Нова задача** → новий `##` блок
- **Продовження/допрацювання** тієї самої задачі → **додати новий `##` блок** з поміткою що це оновлення. Не редагувати попередній запис — дописувати новий, щоб була історія змін
- Якщо файл не існує — створи з заголовком `# Changelog`

### 2. Daily Report — ОБОВ'ЯЗКОВО

Файл: `docs/reports/YYYY-MM-DD-daily-report.md` в директорії проекту.

**Формат:**

```markdown
# Звіт за DD.MM.YYYY

### 1. Назва задачі (коротко)
Опис що зроблено бізнес-мовою, 2-3 речення. Акцент на проблемі яку вирішили та результаті. Як для стендапу — щоб PM зрозумів без технічних деталей.

### 2. Назва іншої задачі
Аналогічно — що було, що зробили, який результат.
```

**Правила daily report:**
- Один файл на день, доповнюється протягом дня
- Кожна задача — окремий `###` блок з порядковим номером і назвою
- Писати українською, неформально, бізнес-мовою
- **Нова задача** → новий `###` блок з наступним номером
- **Допрацювання існуючої задачі** → оновити текст в існуючому `###` блоці (не створювати новий)

**НЕ писати в daily report (і в changelog теж):**
- Технічні/операційні дії: "запустив сервіс", "перезапустив контейнер", "згенерував Prisma клієнти", "запустив тести"
- Проміжні кроки: "прочитав код", "проаналізував файл", "подивився логи"
- Все що не є бізнес-задачею від юзера — лише реальні задачі, фікси, фічі, дослідження

**Приклад:**

```markdown
# Звіт за 18.03.2026

### 1. Розділення Float/Fixed для провайдерів
Адмін тепер може окремо вмикати/вимикати провайдера для плаваючого (float) та фіксованого (fixed) курсу. Раніше був один toggle — тепер два незалежні. Для провайдерів, що не підтримують fixed-rate, toggle автоматично заблокований.

### 2. Безпека 2FA
Доопрацював функціонал 2FA: тестовий код для двофакторки (`000000`) раніше міг випадково працювати на staging. Тепер він працює тільки при явному дозволі і ніколи в production.

### 3. Налаштування markup (комісій) через API
Дослідив, які провайдери дозволяють передавати нашу комісію через API при кожному запиті, а які — тільки через їхній партнерський кабінет. Quickex — через API. BitcoinVN і Changee — тільки через дашборд.
```
